# 网络设计与实测边界

## 1. 四种不同的“服务”

| 组件 | 默认地址 | 作用 | 是否接触媒体 |
|---|---|---|---|
| 信令服务 | `ws://127.0.0.1:5180/ws` | 认证、配对、转发 SDP/ICE | 否 |
| STUN | 用户配置 | 发现 NAT 映射 | 否 |
| TURN | 用户配置 | 必要时中继加密媒体 | 是（作为中继） |
| WebRTC P2P | ICE 协商 | 实际 SRTP 媒体 | 是 |

LinkView 不把以上四件事混为一谈。默认安装不启动 TURN，也不依赖公网服务。

## 2. 信令连接

- WebSocket，文本 JSON，单消息上限 64 KiB，单连接限速 40 条/秒。
- 设备认证：ECDSA P-256 挑战签名；时间偏差 ±2 分钟；挑战 60 秒失效且一次性。
- 服务端只保存：连接对象、设备摘要、会话 ID、配对码哈希/盐、状态与时间戳。
- 单设备最多 2 个并发托管会话；全局连接/会话上限可配置。
- 心跳：服务端默认 180 秒无活动断开；客户端每 30 秒 Ping。
- 生产环境必须使用 `wss://`（反向代理终结 TLS）。当前示例使用 `ws://`，Android 允许明文传输仅用于本地开发。

## 3. 配对与授权

1. 宿主创建 6 位码（密码学随机），默认 5 分钟有效。
2. 配对码以随机盐 + HMAC-SHA256 形式存储在内存；日志/协议不回传哈希。
3. 加入方提交配对码后，服务端遍历“等待加入”的会话做恒定时间校验。
4. 失败尝试按连接计数（5 次后冷却 60 秒）并按来源 IP 窗口限流（5 分钟 30 次，超过封禁 5 分钟）。
5. 即使配对码正确，宿主仍需确认（除非用户显式关闭确认）。
6. 会话是二元的：最多一个宿主、一个加入方；配对码使用后从“可加入”集合移除。

这是有意的纵深防御，但**不能替代** DTLS-SRTP 的媒体加密。

## 4. IPv4 / IPv6 处理

真正的双栈能力体现在候选过滤与回退，而不是地址输入框。

### 4.1 地址分类

`IpAddressTools` 区分：
- IPv4：回环、链路本地（169.254/16）、私有（10/8、172.16/12、192.168/16）、多播、全球单播。
- IPv6：回环、链路本地（fe80::/10）、ULA（fc00::/7）、多播、全局单播、IPv4-mapped。
- 链路本地、回环、未指定地址默认不用于连接。
- IPv6 作用域 ID 只在本地链路有意义，不会被当作全局可达地址。

### 4.2 用户策略

| 设置 | 行为 |
|---|---|
| 自动 | 发送系统产生的可用候选（默认丢弃 IPv6 链路本地） |
| IPv4 优先 | 若本机有可用 IPv4，则等效为仅 IPv4；否则自动回退双栈 |
| IPv6 优先 | 若本机有可用 IPv6，则等效为仅 IPv6；否则自动回退双栈 |
| 仅 IPv4 | 过滤所有 IPv6 候选，即使网络有 IPv6 |
| 仅 IPv6 | 过滤所有 IPv4 候选；没有全局 IPv6 时会失败并在设置中警告 |

过滤同时作用于**本地发出的候选**与**远端接收的候选**，防止对端强制使用被禁用的协议族。SDP 本身不重写，主路径依靠 trickle ICE。

### 4.3 已验证 / 未验证

- 已在本机双栈网卡上成功建立 ICE 连接（候选包含私网 IPv4 与全局 IPv6 地址）。
- **未验证** IPv6-only 局域网、禁用 IPv4 的环境、跨运营商 IPv6、链路本地 IPv6 跨设备直连。
- 不保证任意网络组合都能直连；对称 NAT、企业防火墙、客户端隔离都可能导致失败，需要 TURN。

## 5. 局域网发现

- IPv4 组播：`239.255.76.86:45892`。
- IPv6 组播：`ff12::4c56:45892`（Windows 按接口加入并发送；Android 尽力而为）。
- 广播内容只包含：协议版本、设备 ID、设备名、平台、版本、发现端口、可用地址、能力标签。
- 接收方忽略自己；10 秒未更新即过期。
- 发现结果**仅用于展示**。不能用广播中的设备名或地址作为身份凭据；连接必须经过配对码与宿主确认。
- 常见失败原因：Windows 防火墙、路由器禁用多播、Wi-Fi 客户端隔离、Android 未持有 MulticastLock（应用已申请 `CHANGE_WIFI_MULTICAST_STATE` 并加锁）、VPN 抢占默认路由。
- 自动发现失败时，仍可通过配对码加入；但本版本没有“手动 IP 直接连接”的 SDP 交换通道。手动地址输入仅做格式校验与诊断。

## 6. ICE / STUN / TURN

- SIPSorcery 配置 `RTCConfiguration`：STUN/TURN 列表、`all` 或 `relay` 策略、持续收集候选。
- Windows 端候选收集超时来自 `IceTimeoutSeconds`（下限 3 秒）。
- STUN 探测（诊断页）为标准 Binding Request，校验事务 ID 并解析 XOR-MAPPED-ADDRESS。
- TURN 凭据由用户配置；Windows 用 DPAPI 保存，Android 用 Keystore AES-GCM 保存，不进入普通 JSON。
- **TURN 未实测**：本环境没有 TURN 服务器。仅中继模式在未配置 TURN 时会被设置校验阻止。
- Windows UI 不谎称“直连/中继”：由于 SIPSorcery 未公开稳定的选中候选对读取接口，仅显示“自动（直连优先…）”或“TURN 中继（强制）”及 ICE 状态。

## 7. 连接恢复

- ICE/连接 `disconnected` → `Reconnecting`。
- Windows 在等待 `ReconnectInitialDelayMs × 2^attempt`（上限 `ReconnectMaxDelayMs`）后执行 ICE 重启（host 重新 Offer），最多 `ReconnectMaxAttempts` 次；可关闭自动重连。
- Android 当前只等待并提示失败，未实现自动 ICE 重启；这是已知缺口。
- 会话结束时立即取消信令处理、停止采集、关闭 PeerConnection、清理临时状态。
- 重连失败不会无限重试。

## 8. 诊断页

Windows 诊断（全部真实执行）：
1. 可用 IPv4 / IPv6 地址与接口枚举。
2. 信令健康检查（由 ws/wss 推导 http/https `/healthz`）。
3. DNS 解析（STUN/信令）。
4. 每个 STUN 服务器的 UDP Binding 探测与 RTT。
5. TURN 配置完整性。
6. 当前会话状态/路径策略。

Android 诊断：
1. 网络接口与作用域分类。
2. 信令健康检查。
3. STUN 探测。
4. TURN 配置完整性。
5. MediaProjection 授权说明。

**不会**用一次 ping 或公网连通性断言 WebRTC 一定能建连。

## 9. 实测网络环境

| 环境 | 结果 |
|---|---|
| 本机回环、双栈网卡、无 STUN/TURN | 两个真实 PeerConnection 建连成功；E2E 屏幕传输 PASS |
| 信令服务本机运行 | WebSocket 全流程与 7 项集成测试通过 |
| 跨主机局域网 | 未实测 |
| IPv6-only / 仅 IPv4 | 未实测 |
| 不同子网/路由器/NAT | 未实测 |
| TURN 中继 | 未实测 |
| 公网跨运营商 | 未实测 |

任何未列出的网络环境都不应被假定已经验证。
